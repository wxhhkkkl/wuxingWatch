# Research: 子平格局喜忌引擎（《格局真诠》）

**Feature**: `015-ziping-geju-xiyong` | **Date**: 2026-10-28 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

本文件只记录**本期的技术决策**。领域规则一律以相也《格局真诠》（2018 年版）为准；012–014 期的
旺度口径只在「身强弱」这一处被消费，不作为格局/喜忌的依据。

---

## D1 规则怎么表示：结构化规则对象 + 每个大格一个模块

**Decision**: 49 格写成 `GeJuDefinition` 数据对象；每格由一组 `Condition` 组成；条件用共享的
`conditions.py` 求值器执行。每个大格一个 Python 模块（`rules/zhengguan.py`、`rules/qisha.py`、
`rules/cai.py`、`rules/yin.py`、`rules/shishen.py`、`rules/shangguan.py`、`rules/yangren.py`、
`rules/lujie.py`、`rules/zhuanwang.py`、`rules/huagi.py`、`rules/congge.py`、`rules/zage.py`），
每个条件必须带 `Citation`（章节 + 条件编号 + 页码）。不引入 YAML/DSL 解析库。

**Rationale**: 书的成格条件不是纯布尔表——里面有「有字清格」「财印不碍」「弃尽官星」「有救则复成」
这类**关系性**条件。纯 JSON 表无法表达；硬编码 `if/else` 又不可追溯、不可逐条测试。用「数据对象 +
少量谓词」的混合形态，既能让每条条件单独测试，又能把书证钉在条件上。

**Alternatives considered**:
- 纯 JSON/YAML 规则表 → 条件表达力不足，最终仍要写解释器；且新增依赖。
- 每格写死 `if/else` → 书证、分支、救应无法结构化输出，违反 FR-001/FR-010。
- 通用逻辑编程（Datalog 等）→ 过重，且与项目「无新增依赖」冲突。

## D2 事实层：只提取，不重算

**Decision**: `facts.py` 从既有产出提取 `Facts`：

| 事实 | 来源 |
|---|---|
| 四柱干支 / 藏干 / 十神 | 既有排盘 `pillars` + `constants.shishen` |
| 月令本气 / 中气 / 余气 | 既有 `hidden_stems` 表 |
| 透干（天干是否透出某十神/五行） | 四柱天干 + 十神 |
| 通根 / 强根 | `wan_du.day_master_group` / `degrees` |
| 合化 / 刑冲合害 / 会局 | `wan_du.relations`（established/rejected） |
| 日主组动态旺度 / 档位 | `wan_du.day_master_group` / `wan_du.level` |
| 身强弱（10 度） | 上述日主组动态旺度 |
| 大运逐步旺度 / 日主 | `dayun2` 该步的 `day_master.dynamic` / `level` |

**硬约束**：事实层 MUST NOT 重算旺度、MUST NOT 读 012–014 已删除的 `ge_ju`/`yong_shen` 结论。
日主被天干五合换字时，以 `wan_du.day_master`（换字后）为准，`day_master_original` 仅作展示。

**Rationale**: 这是 FR-004 与 FR-013 的落点——旺度只提供身强弱，其余事实都是「字面/关系」层面的
可观察量。把事实与推理分开，才能用同一份事实同时验证 49 格规则。

## D3 取格：书的三层顺序 + 候选生成

**Decision**: 取格按书的顺序执行：

1. **月令为纲**：月支藏干的本气/中气/余气 → 候选十神格；有透干者优先，但不唯透干。
2. **会合变格**：月令因三合/三会/六合改宗时，以改宗后的月令取格（复用 `wan_du.relations` 的合化结论）。
3. **有官先论官 / 有煞先论煞**：官煞有优先定格权，但以「与月令能组合成什么格」为前提；月令官煞不受损时最纯。
4. **官煞不成再论化气**：按书第十章「先论官煞，再论合化」。
5. **化气不成再论他格（含破格再取）**：月令格破败、与官星构不成格局时，按书另取（弃官就食、弃印就财、去煞存财等）。
6. **外格三前提**：月令无用神、干头无官煞、无财星能立足 → 阳刃/禄劫/专旺/化气/从格/杂格。

**多格并见**：输出主格 + 兼格；主格按上述顺序取第一个成立者，兼格列出其余成立者；若顺序仍不能
唯一确定，标 `open` 并保留候选清单，不静默丢弃。

**Rationale**: 书的正官格总论明确「月令为纲」与「有官先论官」的组合关系；化气章又明确「先论官煞，
再论合化」。把这三处写成一条可执行的顺序，是 49 格判定的骨架。

## D4 成格 / 破格 / 救应：病 → 药 → 复成

**Decision**: 每格的判定分四步：

1. **成格**：书的编号条件逐条求值；书给替代路径的（「或虽有煞也有字清格」）记录所走分支。
2. **破格 / 降格**：按**各格书列的清单**逐条判；正官格的九条中前七类成立且无救应 → 破格，后两类 → 降格；
   其他格按其总论 / 分论的列举分别归类，不得把正官格的九条套到所有格。
3. **救应**：把「病」（破格之字：伤官克官、财坏印、官煞混杂、刑冲破害、食神合官…）与「药」
   （印伏伤、劫合煞、会比冲、财损印…）建模为 `Remedy`；**Remedy 的求值在喜忌层（US3）实现**，
   成破层（US4）只消费其结果；只有药**成立且有效**才判「破而复成」。
4. **高低**：按成破、救应、相神有力、根气、格清格浊判上/中/下。

**Rationale**: 书的核心方法论是「去其忌而存其喜」「有病方为贵」；只判成/破而不判救应，会把大量
「格破有救」的书例误判为破格。救应必须可验证（如「印伏伤」要求印有根、能制伤），不能只看字面出现。

## D5 用神 / 相神 / 喜忌：格神为主，身强弱只作分支

**Decision**:

- **用神** = 格神（该格的主神，如正官格之官、从格之所从之神）。
- **相神** = 辅佐格神者（如正官配印之印、官喜财生之财）。
- **喜神** = 生助用神/相神者；**忌神** = 克破格神/相神或直接破格者。
- **身强弱**只在内格（正官/七煞/财/印/食/伤）与阳刃/禄劫中作为分支；专旺、化气、从格、杂格
  由格本身定喜忌，身强弱不参与（Q1 裁定）。
- **病药**可覆盖默认喜忌：有救应时，忌神可能转为「有病有药」，不得机械输出「见忌即凶」。

**Rationale**: 书对从/化/专旺的喜忌是「以所从之神为用神，以生所从之神为相神，以克所从之神为忌神」
（第十一章），没有身强弱分支；把 10 度分界套上去会得出相反结论。

## D6 大运：每步重取身强弱，允许变格

**Decision**:

- 每一步大运取 `dayun2` 的 `day_master.dynamic` / `level` → 身强弱（10 度）。
- 格名以原局为基准；按书评估**变格**：假从 ↔ 真从、假化 ↔ 真化、破格后另成他格；变格必须输出
  新格名与原因。
- 行运喜忌按书各格的「行运喜忌」规则；成/破/复成逐步标注。
- 流年/流月/流日/流时**不纳入**。

**Rationale**: 书明确「真从不变格，假从容易变格」「假化得运助而成真化」；锁死格名会漏掉大量
行运断语。旺度引擎2 已能逐步给出日主组动态旺度，正好作为身强弱输入。

## D7 书内矛盾：登记，不裁决

**Decision**: `OpenIssue` 记录冲突位置、各说原文、状态（open/resolved）。引擎遇到 `open` 条件时
输出「存疑/未定」，不按任何默认顺序选边；待人工裁定后再补录规则。

**Rationale**: 使用者在 clarify 阶段明确选择「不自动裁决」。这条比「选一个看起来更合理的」更安全：
它把不确定性显式交给使用者，避免引擎用错误规则产出确定结论。

---

## D8 书例回测：fixture + runner，不设一致率门槛

**Decision**:

- 从书中抽取 ≥100 例**带明确格名**的命例，写入 `fixtures/book-cases-geju.json`：
  `id / source（章/节/页）/ pillars / book_ge / book_cheng_po / book_xi_ji / book_gao_di / notes`。
- `cases.py` 逐例运行引擎，输出一致/分歧清单；每条分歧归因到具体规则/条件。
- 不设统一一致率门槛（与 012 期对拍口径一致）；按大类报告一致率。
- 书中只有过程分析、没有明确格名的例子不作格名断言锚点。

**Rationale**: 书的命例是最接近「客观真值」的验收锚点；但书例本身有省略、有作者主观取舍，
统一一致率门槛会逼着实现去拟合个例。逐例归因更符合项目的对拍传统。

## D9 49 格落地：内 27 → 外 22，每格必须有血有肉

**Decision**: 每个大格一个模块；每格声明 `GeJuDefinition`，含成格条件、破格/降格、救应、用神/相神/
喜忌、高低、行运喜忌、书证。禁止空壳格；无书证的条件不得进入规则表。书明确批判的「无理杂格」
仍给出定义与 `status: "reserved"` 标注，但不强行入格。

**Rationale**: 49 格全量是使用者拍板的范围；但「全量」不等于「每格都同样成熟」。用 `status`
把「已实现 / 存疑 / 保留」分开，既满足覆盖，又不伪造确定性。

## D10 API：纯增量、按需实时、不落库

**Decision**:

- `POST /api/charts/geju`：请求 = `BirthInput` + 可选 `dayun_ganzhi`；不传则返回原局 + 全部大运步。
- `GET /api/records/{id}/geju`：从记录输入当场重推（与 `/records/{id}/dayun2` 同模式）。
- 响应含 `engine`、`version`（规则表哈希）、`yuanju`、`dayun_steps`、`open_issues`、`degradations`。
- 现有 `/predict`、`/dayun2`、`/liushi`、记录端点**契约不变**。

**Rationale**: 与 014 的「按需实时、不落库」一致；避免 `chart_result` 膨胀与版本迁移。规则表哈希
让「同一输入、不同规则版本」可追溯。

## D12 确定性与性能

**Decision**: 规则按固定顺序遍历（内格→外格、格内条件编号顺序）；禁止直接迭代裸 `set`；输出清单
按 `GAN_ORDER` / `ZHI_ORDER` 排序。纯函数、单盘毫秒级；不落库、不批处理。

**Rationale**: 沿用 012 期 FR-058 的确定性要求；同一输入在任何进程、任何顺序下必须逐位一致。

## D13 测试策略（TDD）

**Decision**:

1. **规则单测**：每条 `Condition` 单独测试（真/假/缺数据）。
2. **引擎单测**：取格优先级、成破/救应、用神/喜忌、高低、大运变格。
3. **契约测试**：两个新端点的响应形状、错误码、记录重推。
4. **书例回测**：≥100 例逐例比对与归因。
5. **回归**：现有旺度/引擎2 的 667 盘基线与既有测试逐位不变；前端既有 185 条测试全绿。

**Rationale**: 宪法 II 要求测试先行；49 格规则多、分支多，必须把「条件」与「组合」分开测。

---

## D14 缺时柱与降级

**Decision**: 三柱输入时，事实层仍产出可判部分；凡依赖时柱的格/条件（时上偏财、时上一位贵等）
标 `degraded`，无法判定的输出「未定」并列出缺失项。大运仍按引擎2 的三柱路径取数。

**Rationale**: 现有产品已支持缺时柱；新引擎不得因为缺时柱而整盘拒绝。

---

## D15 记录与版本

**Decision**: 不把格局结论写入 `chart_result`。记录侧端点按记录输入重推；响应带 `rules_version`
（规则表源码哈希），便于判断「同一输入、不同规则版本」的差异。旺度版本由既有排盘响应单独提供，不并入本响应。

**Rationale**: 规则表会随书例回测不断修订；若落库，旧记录会冻结在旧规则。按需重推始终给当前口径。

---

## D16 术语

**Decision**: `terms.py` 维护「书中原词 → 产品常用名」映射（七煞/七杀、阳刃/羊刃、印绶/正印/偏印、
枭印/偏印等）。规则文本与书证用书中原词；API 同时带 `name` 与 `aliases`；UI 展示「书术语（常用名）」。

**Rationale**: 书证必须可逐字对回原书；用户界面又要与产品已有十神叫法一致。两者都需要。
