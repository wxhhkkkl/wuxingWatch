# Research: 真太阳时十二时辰精确划分

**Date**: 2026-08-10 | **Feature**: specs/003-true-solar-shichen

Technical Context 中无 NEEDS CLARIFICATION（无新技术选型）。以下为设计研究项的决策记录。

## R1: 24 段窗口如何覆盖全天任意出生时刻

**Decision**: 以"日出日"为窗口单位。对出生日期 D，需要三天的天文数据：D-1 的日落与正午（推 D-1 子夜）、D 的日出/日落/正午/子夜、D+1 的日出。构造两个候选窗口：
- 窗口 A（始于 D-1 日出…简化为 D-1 日落→D 子夜→D 日出 段）：覆盖 00:00 至 D 日出的出生
- 窗口 B（始于 D 日出）：覆盖 D 日出至次日日出的出生

实现上简化为：分别计算"包含出生时刻的子夜"与"包含出生时刻的正午"所属的那组四区间。具体做法——取出生时刻之前最近的太阳子夜 M（D 日子夜 = D 日正午+12h；若出生 < D 日子夜则 M = D-1 日子夜），则窗口 = [M 所属日出, M+12h 正午, …]；即从 M-δ 的日出到 M+24h 附近的次日日出，四区间为 日出→正午→日落→子夜→次日日出。取窗口起点日出 = M 之前最近一次日出（用 D 与 D-1 两日的 sunrise_sunset 即可覆盖）。

**Rationale**: 出生时刻可能落在 00:00–日出之间（属于前一"日出日"的窗口），只算当日数据会漏判；用"出生时刻之前最近的子夜"反推窗口起点，逻辑统一且不依赖窗口编号。
**Alternatives considered**: 固定按民用日 D 算窗口、日出前出生报错——被否（漏夜生用户）；总是算 D-1/D/D+1 三天全套数据再拼接——被否（计算量 3 倍，仅需两次 sunrise_sunset + 一次 solar_noon_midnight 即可覆盖）。

## R2: 时柱天干推导（五鼠遁）

**Decision**: 时干 = `GAN[(day_gan_index % 5) * 2 % 10 + zhi_index]`（zhi_index：子=0…亥=11），即"甲己还加甲，乙庚丙作初"。不依赖 lunar-python 的时辰计算（其按钟表小时，与本功能的事件锚定分段不同）。lunar-python 仅用于：① 夜子时时取 D+1 的日柱干支（`Solar.fromYmd(D+1).getLunar().getDayGan/Zhi()`）；② 验证单测参考值。
**Rationale**: 五鼠遁是纯干支算术，工程上比改造 lunar-python 的 EightChar 更可靠、可单测。
**Alternatives considered**: 构造"合成时刻"喂给 lunar-python（把归属时辰映射回代表钟点）——被否：日柱换日与时辰同时改变时合成时刻语义混乱，且引入隐式依赖。

## R3: 精确模式下派生字段的重算范围

**Decision**: 仅重算时柱、（夜子时的）日柱、日主、四柱十神、喜忌分析。大运、胎元、命宫、身宫、人元司令保持原盘不变。
**Rationale**: FR-006 明确"年柱/月柱计算规则保持不变"，spec 未要求重算其他派生项；大运起运依赖节气距离（出生民用时刻未变）、命宫身宫依赖月支+时支的钟表定义，改动将超出 spec 范围（原则 III）。此范围决策已在 plan 中显式记录，实现时如用户另有要求再调整（原则 IV/V）。
**Alternatives considered**: 全部派生字段按新日柱/时柱重算——被否：超出 spec，且大运/命宫规则属于另一套钟表体系，混合两套规则反而自相矛盾。

## R4: 可视化形式

**Decision**: SVG 圆形表盘（24 扇形环）。外圈 24 段按真实起止角度绘制（以子夜为 12 点方向起算，角度 = 时刻/24h × 360°），昼弧（日出→日落）与夜弧分色；四个关键时刻用图标/短线标记；出生时刻用醒目指针；每时辰标签（子丑…）置于扇区外侧；中心显示归属时辰。退化方案：表盘下方附 12 时辰起止表格（小屏可读性兜底）。
**Rationale**: 圆形表盘直观对应"一日循环"，子夜/正午分居下/上，符合用户对钟面的心智模型；24 段在圆周上每段至少 15°，360px 屏上标签可读（SC-005）；手写 SVG 无新依赖（宪法 I/III）。
**Alternatives considered**: 横向 24h 时间轴——被否：24 段在 360px 宽下每段约 15px，标签拥挤需横滚（违反 US3 场景 3）；引入 echarts 等图表库——被否：新依赖且表盘需求简单，YAGNI。

## R5: 极昼/极夜回退的锚定

**Decision**: 日出或日落任一缺失即回退：以当日太阳正午为中心，午时 = [正午-1h, 正午+1h]，其余时辰按 2h 等距向两侧展开（即 24 段每段 1h，子时中心对正子夜=正午+12h），`fallback=True` 并在详情页提示。
**Rationale**: 与 clarify 后统一的"民用时刻比较"基准一致；正午/子夜只依赖经度+均时差，极区依然可求。
**Alternatives considered**: 极区直接报错——被否（FR-011 要求回退不阻塞）；用 45°N 等"参考纬度"估算日出日落——被否：虚构数据，违背诚实原则。

## R6: 开关持久化

**Decision**: 登录用户选择写入 `localStorage["precise_shichen"]`，Home 页加载时读取；未登录用户仅内存态（页面刷新即复原默认关）。
**Rationale**: FR-012 为 SHOULD，localStorage 满足"记住偏好"且零后端改动；不存后端用户表（避免 schema 变更，原则 III/IV）。
**Alternatives considered**: 存用户表新列 / 用户偏好接口——被否：为一个布尔开关加 DB 迁移与 API 过度设计。
