请求体 `BirthInput` 与排盘字段**一概不动**（同 012 契约 §1）。喜忌结论子树 `xi_yong.strength` 的**原局部分形状与取值均不变**（FR-022 / FR-023）。

**硬约束**：`backend/src/api/routers/records.py` 的 `_summarize()` 直接读 `result["pillars"]`——排盘字段不得变动。

## 2. 新增端点 —— 岁运推导（按需、不落库）

按 FR-021a，两个入口各一个薄端点，**同一实现**：

### 2.1 `POST /api/charts/suiyun` —— 新排盘路径

```jsonc
// 请求：BirthInput（同 /predict） + 选中项
{
  "…": "同 BirthInput 的全部字段",
  "dayun_ganzhi": "辛丑",        // 必填：选中哪一步大运（须是该盘的合法步）
  "liunian_year": 2003           // 可选：给了则同时算阶段 3；不给则只返回阶段 2
}
```

### 2.2 `GET /api/records/{id}/suiyun` —— 已保存记录路径

```jsonc
// 查询参数
? dayun_ganzhi=辛丑 & liunian_year=2003      // liunian_year 可选
```

后端按该记录的 `_input`（出生信息或四柱）**当场重推大运与流年**——**不得**读取该记录里任何已保存的岁运结论（FR-021a / FR-026）。

### 2.3 响应（两端点同形）

```jsonc
{
  "engine": "wangdu-v2",
  "contract_version": 2,
  "stage": 2 | 3,                 // 给了 liunian_year 即 3
  "input_scope": "four_pillars" | "three_pillars",
  "degradations": [ … ],          // 无出生日期 / 未起运 / 缺时柱时的降级说明（FR-025）
  "dayun":   { …阶段 2 结论（见 §3）… },
  "liunian": { …阶段 3 结论（见 §4）… },   // stage==2 时为 null
  "pairs":   [ …成对呈现（见 §5）… ]       // stage==2 时为 null
}
```

**校验规则**：
- `stage == 2` ⟺ `liunian == null` ∧ `pairs == null`（R-1）。
- `dayun.source == "dayun"`，`liunian.source == "liunian"`（R-2）。
- **响应中不得出现任何吉凶字段**（`verdict` / `jixiong` / `ji` / `xiong`）——FR-016a（R-3）。
- 无出生日期（四柱输入模式）或尚未起运时，该盘**没有可传的合法大运步**，端点以 **422** 明示拒绝（`detail` 写明「不在该盘的大运步内」），而不是静默算一个别的步（R-4）。
  > **2026-09-21 实现后修订**：本规则原写作「返回 200 且 `degradations` 非空、`dayun`/`liunian` 均为 `null`」。实现改为**客户端降级 + 端点 422**——因为请求体里 `dayun_ganzhi` 是必填的，而这两种盘**根本不存在合法取值**，客户端也就在调用前就能判定不可用；再由端点回 200 空结论，反而要客户端传一个编造的大运干支。FR-025 要求的是「降级并明示原因」，两种路径都满足，而 422 不会把「不可用」伪装成「算过了」。降级提示的呈现见 `frontend/src/utils/suiyun.ts`。
- 同一请求两次调用的响应**逐位一致**（沿 012 的确定性要求）（R-5）。

## 4. 阶段 3 —— `liunian` 条目

形状与 §3 同构，另加 `ganzhi_context.liunian`（含 `year`），`source` 为 `"liunian"`。

**参与矩阵**（本期口径，须在实现与测试中逐项守住）：

| 项 | 流年是否参与 | FR |
|---|---|---|
| 刑冲合害、藏干度数、五行旺度 | **参与**（适用流年独立档：四墓库藏干 / 未克申酉 / 辰戌丑未冲三处） | FR-014 / FR-015 |

| 调候、格局层次 | **参与**，同口径重判 | FR-021c |
| **综合（折中）状态** | **不参与**——折中只取月令与大运 | FR-003 / FR-017a |
| **吉凶结论** | **不产出** | FR-016a |

## 5. `pairs` —— 两阶段成对呈现（FR-016c / SC-009）

```jsonc
"pairs": [
  { "key": "yong_shen.theoretical.element", "label": "用神",
    "dayun":   { "value": "土",   "source": "dayun" },
    "liunian": { "value": "水",   "source": "liunian" },
    "changed": true },
  …
]
```

**校验规则**：
- `key` 集合 MUST 覆盖 7 类：用神 / 喜神 / 忌神 / 旺度档位 / 格局 / 调候 / 格局层次（FR-016c）（R-6）。
- 每对**两侧都必须在**，不得只给一侧（FR-016c）（R-7）。
- `pairs` 中不得出现吉凶类字段（FR-016a）（R-8）。

## 7. 命盘图的岁运维度 —— **已确认：方案 A**（research R7）

### 7.1 现状（问题陈述）

`frontend/src/utils/relations.ts`（861 行）是**前端的关系判定第二实现**；`RelationDiagram.vue:125-148` 的取数是**混合来源**——
原局取后端、选中大运时优先用后端该步裁定、**流年维度仍由前端本地补判**（该文件 `:134` 自陈「临时状态」）。
其自建列序（大运, 流年, 年, 月, 日, 时，`:54-87`）与后端的（…年,月,日,时,大运,流年）**相反**。

**本期风险**：013 让后端**按年**产出流年裁定后，前端若继续本地补判，则同一命盘同一年份**两个页面显示不同结论**——违反 FR-024 / SC-008。

### 7.2 方案 A（**已采纳**）—— 命盘图的岁运维度改为只消费后端产出

命盘图不再本地判一次，改由后端按阶段返回关系裁定（阶段 2 经 `strength.dayun[]`、阶段 3 经 §2 的端点）。前端 `relations.ts` 的**岁运相关部分随之退役**；其自建列序（大运,流年,年,月,日,时）与后端相反的问题一并消失。

**范围边界**：`relations.ts` 的**原局部分**（861 行里的刑冲合害判定、藏干度数表、四墓库表等）**是否同步退役不在本期范围**——整体退役是更大的架构变更，另议。

### 7.3 方案 B（未采纳）—— 仅同步重写 TS 副本口径

保留双实现，把 `relations.ts` 的岁运口径对齐后端。**漂移仍会复发**（011/012 已两度吃亏）。

### 7.4 方案 C（未采纳）—— 本期不动

命盘图的岁运维度维持前端本地判，**与 FR-024 / SC-008 直接冲突**。

**裁定（2026-09-21 用户确认）**：按**方案 A** 实施。任务拆分须含「前端岁运维度改消费后端 + 相关前端测试改写」。
