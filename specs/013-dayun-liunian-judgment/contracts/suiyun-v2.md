请求体 `BirthInput` 与排盘字段**一概不动**（同 012 契约 §1）。喜忌结论子树 `xi_yong.strength` 的**原局部分形状与取值均不变**（FR-022 / FR-023）。

其 `strength.dayun[]`（阶段 2）在本期**增补三个字段**（形状扩展、值允许变），见 §3。

**硬约束**：`backend/src/api/routers/records.py` 的 `_summarize()` 直接读 `result["pillars"]`——排盘字段不得变动。

## 2. 新增端点 —— 岁运推导（按需、不落库）

按 FR-021a，两个入口各一个薄端点，**同一实现**：

### 2.1 `POST /api/charts/suiyun` —— 新排盘路径

```jsonc
// 请求：BirthInput（同 /predict） + 选中项
{
  "…": "同 BirthInput 的全部字段",
  "dayun_ganzhi": "辛丑",        // 必填：选中哪一步大运（须是该盘的合法步）
  "liunian_year": 2003           // 可选：给了则同时算阶段 3；不给则只返回阶段 2
}
```

### 2.2 `GET /api/records/{id}/suiyun` —— 已保存记录路径

```jsonc
// 查询参数
? dayun_ganzhi=辛丑 & liunian_year=2003      // liunian_year 可选
```

后端按该记录的 `_input`（出生信息或四柱）**当场重推大运与流年**——**不得**读取该记录里任何已保存的岁运结论（FR-021a / FR-026）。

### 2.3 响应（两端点同形）

```jsonc
{
  "engine": "wangdu-v2",
  "contract_version": 2,
  "stage": 2 | 3,                 // 给了 liunian_year 即 3
  "input_scope": "four_pillars" | "three_pillars",
  "degradations": [ … ],          // 无出生日期 / 未起运 / 缺时柱时的降级说明（FR-025）
  "dayun":   { …阶段 2 结论（见 §3）… },
  "liunian": { …阶段 3 结论（见 §4）… },   // stage==2 时为 null
  "pairs":   [ …成对呈现（见 §5）… ]       // stage==2 时为 null
}
```

**校验规则**：
- `stage == 2` ⟺ `liunian == null` ∧ `pairs == null`（R-1）。
- `dayun.source == "dayun"`，`liunian.source == "liunian"`（R-2）。
- **响应中不得出现任何吉凶字段**（`verdict` / `jixiong` / `ji` / `xiong`）——FR-016a（R-3）。
- 传进来的 `dayun_ganzhi` **不在该盘的大运步内**（含「该盘尚未起运、根本没有步」）时，端点以 **422** 明示拒绝（`detail` 写明「不在该盘的大运步内」），而不是静默算一个别的步（R-4）。
  > **2026-09-21 实现后修订**：本规则原写作「无出生日期（四柱输入模式）时返回 200 且 `degradations` 非空、`dayun`/`liunian` 均为 `null`」。实现改为**客户端按情况降级 + 端点只在参数不合法时 422**，理由两条：
  > ① 请求体里 `dayun_ganzhi` 必填，而**非法步**（含尚未起运）根本没有正确取值可传——回 200 空结论反而要客户端编一个大运干支；422 不会把「不可用」伪装成「算过了」。
  > ② **四柱输入模式其实排得出大运干支**（步序与起运无关，只是 `start_year` 为 null），故**阶段 2 是可算的**——一刀切降级会把一个能算的结论挡掉。真正缺的是**年份**：定不出「当前所处大运」，也定不出某一步覆盖哪些流年。故 FR-025 的三类盘在客户端这样分：**尚未起运** → 两页都降级；**无出生日期** → 「加入大运」页照常可用（按干支选步、不显示年份），「加入流年」页降级；**时辰不详** → 不阻断，仅明示缺时柱那一维。
  > 降级的呈现见 `frontend/src/utils/suiyun.ts`；三条路径各有测试（`frontend/tests/SuiyunPages.spec.ts`）。
- 同一请求两次调用的响应**逐位一致**（沿 012 的确定性要求）（R-5）。
- `stage == 2` 时，`steps[*].chart.pillars`（含 `charts[*].chart`）**MUST NOT** 出现
  `key == "_liunian"`；阶段 3 若该年流年被大运挡住（门控，见 §4/FR-019）同样 MUST NOT
  ——那一列的度数与本步实际旺度不符，补上就是伪依据，故后端**不建**它，前端出灰显占位
  （`frontend/src/components/StepChart.vue` 的 `placeholders`）。**判据只能是「有没有这一列」**：
  `analyze_step` 的门控**不清** `item["liunian"]`（它仍是传入的干支），拿它当判据会画错（R-9）。

## 3. 阶段 2 —— `dayun` 条目（在 012 §8 基础上扩展）

```jsonc
{
  "source": "dayun",                    // 【新增】
  "ganzhi": "辛丑", "start_year": 2021, "start_age_xu": 51,
  "level": "偏弱",                       // 该步旺度档位
  "ge_ju": { "type": "cong_ruo", … },
  "yong_shen": { "theoretical": {…}, … },
  "tiaohou": { … },                     // 【新增】按该步同口径重判（FR-021b）
  "layers":  { … },                     // 【新增】按该步同口径重判（FR-021b）
  "transition": "破格" | "成格" | null,
  "relations": { "established": [...], "rejected": [...] },
  "deltas": [ … ], "scores_after": { … },
  "steps": [ … ]                        // 依据段（见下方「快照里的岁运两列」）
}
```

**快照里的岁运两列**（2026-09-22 补遗；FR-027）——`steps[].chart` 与 `steps[].charts[].chart`
的 `pillars` 在本端点下**含岁运列**：两页的命盘要比原局页多出四个字（大运、流年并排在
四柱**左边**；本端点把它们**追加在四柱之后**，显示顺序由前端重排）：

| 事项 | 口径 |
|---|---|
| 何时有 `_dayun` | 阶段 2、3 **恒有**（该步大运必参与） |
| 何时有 `_liunian` | **仅阶段 3 且未被门控挡住时**。校验规则见下 R-9 |
| `label` | `大运` / `流年`（四柱仍为 `年/月/日/时`） |
| 岁运之干 `gan_degree` | `1` 度（即「运干同类相助 +1」）；合而不化者按**成数**缩放并置 `gan_change="合绊"`，合化成功置 `gan_change="合化"` + `gan_original` 为原字 |
| 岁运之干 `gan_own` / `gan_root` | **恒为 `null`**——「主数 = 自身 + 根」对不建组、不通根的岁运之干不成立 |
| 岁运之支 `hidden` | 取 `is_dayun` / `is_liunian` **独立档**（书 上 399-403 / 449-451 / 491-497），**平加、不乘月令系数**（书 上 884），且 `change` 恒为 `null`（不与原局藏干表比对） |

> **与入库路径的有意差异**：`strength.dayun[].steps[].chart`（`analyze_all` 的产物，写进
> `chart_result`）**仍为四柱**——那 64 张快照每张再加两列是纯增负，且原局页并不画它。
> 两条路径都出自 `pipeline.compute_strength`，靠 `suiyun_columns` 形参分流
> （默认 `False`）。**这不是 bug，勿「修」**。

**一致约束（FR-022a / SC-007）**：原局页「用神随大运变化」一行显示的用神，与阶段 2 结论里**同一步大运**的用神 MUST 逐项相同——两页不得并存两套大运口径。

## 5. `pairs` —— 两阶段成对呈现（FR-016c / SC-009）

```jsonc
"pairs": [
  { "key": "yong_shen.theoretical.element", "label": "用神",
    "dayun":   { "value": "土",   "source": "dayun" },
    "liunian": { "value": "水",   "source": "liunian" },
    "changed": true },
  …
]
```

**校验规则**：
- `key` 集合 MUST 覆盖 7 类：用神 / 喜神 / 忌神 / 旺度档位 / 格局 / 调候 / 格局层次（FR-016c）（R-6）。
- 每对**两侧都必须在**，不得只给一侧（FR-016c）（R-7）。
- `pairs` 中不得出现吉凶类字段（FR-016a）（R-8）。

## 7. 命盘图的岁运维度 —— **已确认：方案 A**（research R7）

### 7.1 现状（问题陈述）

`frontend/src/utils/relations.ts`（861 行）是**前端的关系判定第二实现**；`RelationDiagram.vue:125-148` 的取数是**混合来源**——
原局取后端、选中大运时优先用后端该步裁定、**流年维度仍由前端本地补判**（该文件 `:134` 自陈「临时状态」）。
其自建列序（大运, 流年, 年, 月, 日, 时，`:54-87`）与后端的（…年,月,日,时,大运,流年）**相反**。

**本期风险**：013 让后端**按年**产出流年裁定后，前端若继续本地补判，则同一命盘同一年份**两个页面显示不同结论**——违反 FR-024 / SC-008。

### 7.2 方案 A（**已采纳**）—— 命盘图的岁运维度改为只消费后端产出

命盘图不再本地判一次，改由后端按阶段返回关系裁定（阶段 2 经 `strength.dayun[]`、阶段 3 经 §2 的端点）。前端 `relations.ts` 的**岁运相关部分随之退役**；其自建列序（大运,流年,年,月,日,时）与后端相反的问题一并消失。

**范围边界**：`relations.ts` 的**原局部分**（861 行里的刑冲合害判定、藏干度数表、四墓库表等）**是否同步退役不在本期范围**——整体退役是更大的架构变更，另议。

### 7.3 方案 B（未采纳）—— 仅同步重写 TS 副本口径

保留双实现，把 `relations.ts` 的岁运口径对齐后端。**漂移仍会复发**（011/012 已两度吃亏）。

### 7.4 方案 C（未采纳）—— 本期不动

命盘图的岁运维度维持前端本地判，**与 FR-024 / SC-008 直接冲突**。

**裁定（2026-09-21 用户确认）**：按**方案 A** 实施。任务拆分须含「前端岁运维度改消费后端 + 相关前端测试改写」。
